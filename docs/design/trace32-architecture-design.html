TRACE32 脚本工程化设计

把「手动点 GUI 抓现场」变成「一条命令产出可复现的报告」——
从本仓库的实测现状、Linux 内核与 Lauterbach 官方工程惯例，推导出一套可落地的目录/契约/门禁/迁移方案。

文档docs/design/trace32-architecture-design.html（自包含，无外部依赖，可离线打开、可打印）
读者要接手这套脚本的人 / 要把它工程化的人 / 学习者（每节末尾有 学习要点）
依据本仓库实测 + 本机 Lauterbach 官方 demo（<T32_INSTALL>\demo\arm）。凡引用的路径、行号、体积均为实测
状态设计文档（方案 v2）。不含代码改动承诺；迁移见 §7，需逐项拍板
不适用不评价客户脚本质量；不修改只读资产（third_party\、cmm\src_2210\、ramdump\）
怎么读这份文档 ① 先读 §1 明白疼在哪 → ② §2/§3 看业界与官方怎么做 → ③ §4/§5 看目标长什么样 → ④ §6 看怎么防回归 → ⑤ §7 看怎么一步步走过去。§8–§10 是查阅用的对照表与索引。
一句话 设计的核心不是"写更多脚本"，而是把已经跑通的确定性固定成契约，让 GUI、CLI、Python、AI 四个消费者都从同一份真相出发。

0三十秒摘要

本仓库已经跑通了一条完整的无人化链路：2211 死机现场 → 13 段无 GUI 分析 → 报告 + 离线堆统计 → 与客户 GUI 的黄金基准判等价。 它证明了三件事：无头可行、文件契约可行、客户脚本可以一行不改地复用。剩下的问题不是能力，而是形状：地址写死在脚本里、平台差异靠人写分支、输出格式随脚本心情、门禁只覆盖了跑得通的部分。

1为什么需要设计

1.1 现状五层：它已经是一套架构，只是没有写下来

图 1-1 · 现状分层（左：层名；中：盘上实体；右：该层的"接口"是什么）
L5
人 / AI读差异、定位是"解析器 bug / 固件 bug / 用例设计 bug"
接口：报告与 diff，不是调试器窗口
L4
离线分析（纯 Python）tools\heap_stats_offline.py、tools\check_entries_equiv.py
接口：读 dump/报告字节，毫秒级、可并发、无需 license
L3
文件契约out\runs\ · out\logs\ · tests\*.sha256 · tests\smoke\*.markers · cmm\functions.json
接口：结论走文件，不走 stdout/退出码
L2
TRACE32 + PRACTICEconfigs\ → local\（占位符展开）→ cmm\ + third_party\vendor\2210_trace32\（t32 的 CWD）
接口：-c <cfg> -s <script>；客户脚本零改动
L1
驱动器（PowerShell）cli\run_smoke.ps1 · cli\run_2211_ap.ps1 · cli\run_2211_func.ps1 · tests\run_all.ps1
接口：起进程、超时兜底、杀 t32*、断言 marker
L0
数据面（只读）ramdump\2211_deathscene\（9 件 / 35.6 MB，含客户 GUI 原件 ap_PrintData.txt 2.8 MB）
接口：SHA256 清单；任何人不改

为什么用语言而不是"风格"来分这五层？因为每一层的能力边界是被工具卡死的（详见 §8 对照表）：

PRACTICE
唯一能进调试核的语言，也是客户的语言
PowerShell
唯一能在 t32 挂死时救场（可杀进程、可超时）
Python
唯一能无 license、可并发、毫秒级算字节
JSON / .t32
是契约不是程序：人和机器都读得懂
"分层"不是为了好看。判断一个新东西该放哪层，只问一句：它读什么、写什么？读 dump 写报告 → L4；读参数进调试核 → L2；把结论变成一个可 diff 的文件 → L3。

1.2 三个真实事故：设计缺陷的第一次代价

图 1-2 · 三个事故的因果链（都发生在"用客户 2210 脚本提取 2211 现场"那一轮）
事故 A：零输出死循环客户 print_dlmalloc_heap.cmm 外层空闲链遍历 没有环检测
→
现象脚本永不返回、报告不落盘；只有 marker 证明它跑过
→
我们的对策自写有界 walker cmm\heap_summary.cmm：步数预算 + 两道缺失守卫 + 每 0x1000 步进度 marker
▼
事故 B：原地自旋另一个客户脚本 print_mem_summary_by_file.cmm 的块推进缺 size==0 守卫
→
现象同样静默；监控 480 s 无进展
→
我们的对策两个客户堆脚本一律不进无头链，改由注册表标记 safe:false，等价判定里记为 partial/no
▼
事故 C：报告被截断TRACE32 的 print AREA 只在 16 KB 缓冲满、或 AREA.Close 时把内容写盘
→
现象杀掉进程后报告恰好 16384 B / 227 行，而 marker 已到第 8 段 ⇒ 后面几段输出全丢
→
我们的对策整链必须跑到 AREA.Close；marker 作为独立进度通道存在；超时值从 300 s 提到 900 s
三个事故的共同点：它们都不是"脚本写错了"，而是"没有契约"——进程不会被超时保护、报告没有完整性凭据、输出目录没有原子落盘语义。设计要补的正是这些。
这里有两处关于我自己的诚实记录，因为它们是这套设计的直接理由：
① 我曾用 [System.Text.Encoding]::Latin1 做二进制提取——该类型在 Windows PowerShell 5.1 下不存在（返回 $null），于是所有敏感信息探针静默假报"无命中"；正确写法是 GetEncoding(28591)。
② 我曾把"目标目录不存在导致 APPEND 静默失败"误判成"相对路径不生效"，得出过一条错误的铁律。⇒ 凡是靠落盘判定的实验，必须先确认目录存在，并用绝对路径标记证明脚本真的执行过。

体检数字里最值得注意的一栏是「2210 平台的真实机器路径依赖 = 2 处」。它说明：这套脚本离"换台机器就能跑"只差两个配置值。所以设计的重心不该是"抽象更多"，而是"把剩下的 2 处收进配置、把地址收进数据、把差异变成可 diff 的断言"。
看数字的方法：不要看"有多少脚本"，要看"有多少处人写的绝对值"。地址、路径、结构体偏移、线程名——每一处手写值都是一个未来会静默出错的地方。

2参照系 A：Linux 的七条惯用法 → TRACE32 对应物

不要把 Linux 当"另一个项目"抄，而是当一个成熟内核工程如何组织"多平台 + 多配置 + 可回归"的经验来读。下面七条都能在本仓库找到落点。

图 2-1 · 惯用法映射（左边是 Linux，右边是我们的目标形态，中间是"为什么能对应"）
Linux 惯用法→TRACE32 对应物为什么能对应
arch/ 与 kernel/ 分离→platforms\<p>\ 与 core\平台相关的地址/符号是"arch"，跨平台的分析流程是"kernel"。现状：两者混在 cmm\ 与 vendor\ 之间
Kconfig + .config→configs\ 分层 + platform.json"选什么"是数据；一次运行 = base + mode + target 三份拼一份
make / make run→统一入口（make run PLATFORM=2210 FEATURE=heap）把"跑什么"变成一条可复制、可进 CI 的命令行
make O=out/（源外构建）→out\runs\ / out\logs\ ✅ 已做产物与源码同目录会污染 diff、被误提交。我们已经把 runs\+logs\ 收进 out\ 并忽略
checkpatch.pl→tools\t32lint.py把"踩过的坑"变成机器可查的规则：禁 DIALOG.*、禁绝对路径、WHILE 必须有步数上限
selftests/→tests\{lint,unit,golden,matrix}分层：贴规则的、不做 I/O 的、要与黄金基准比的、跨用例矩阵的，混在一起就没法挑着跑
MAINTAINERS / CODEOWNERS→OWNERS只读资产（third_party\、ramdump\）明确标"只读、改动需评审"
图 2-2 · 一条命令的旅程（现状 vs 目标）
现状人手 cd 到仓库根 → 手动展开 local\*.t32 → powershell -File cli\run_2211_ap.ps1 → 看 out\runs\<stamp>\
⟹
目标make run PLATFORM=2210 FEATURE=all
展开、起停、超时、断言、结构化输出、判定，一条命令全包
关键差别不在"少敲几个字"，而在命令行即文档：CI、他人、AI 都能从这一行反推出依赖与产物。
Linux 真正值得学的是"分层 + 数据驱动 + 可回归"这三件事，而不是目录名。能不能把这三件事落进一个只有 21 个 .cmm 的小仓库？能——但要点到为止，见 §4.1 的取舍。

3.1 导出侧：一个脚本、两个入口，产物是「可自恢复包」

ramdump.cmm 头部自己写的 Usage（原文照抄）：

; Usage: ; - Interactive: ; DO <path_to>/ramdump.cmm ; Edit the settings in the dialog and then hit "STORE". ; - Script based: ; DO <path_to>/ramdump.cmm \ ; MEM="<comma separated list of absolute memory ranges>" \ ; SYMBOLFILE="<path to symbolfile>" TRACESAVE=<0|1> STOREFORMAT=<0|1>

骨架只有七行（L44–60，原文）：

PRIVATE &sArguments
PRIVATE &bDialog &sMemoryRanges &sSymbolFile &bTraceSave &nStoreFormat
ENTRY %LINE &sArguments                       ; ← %LINE = 整行剩余参数（一个"参数包"）
GOSUB checkSanity
GOSUB parseArguments "&sArguments"
RETURNVALUES &bDialog &sMemoryRanges &sSymbolFile &bTraceSave &nStoreFormat
IF (&bDialog)                                 ; ★ 交互只是一个可选分支
(
  GOSUB showDialog
  ENDDO
)
图 3-2 · 「同一份代码服务 GUI 与 CLI」——官方写法 vs 我们的写法
官方：分支在里面（L44-60）
DO ramdump.cmm MEM="..." \
   SYMBOLFILE="..."          ; 无对话框
           │
           ▼
   parseArguments
           │
      IF (&bDialog) ──► showDialog   ; 只有真交互才弹
一份文件、一个入口、零重复。
我们：外壳在外面
gui\config_sim.t32 + .lnk
        │
        ▼
LM620_Restore.cmm   ; 27 处 DIALOG
        │  do restore.cmm "&ramdump" "&elf"
        ▼
cli\2211_ap_func.cmm.tmpl → local\func_*.cmm
                            ; 无头外壳
两份外壳、同一内核；能跑，但重复。
结论：要"统一抽象"，正确做法不是重写客户脚本，而是把 DIALOG 收进一个 showDialog 子程序，由 ENTRY %LINE 的参数包决定走哪条。这一步只有在 src_2210 真正成为"我们自己的代码"之后才做（见 §7 步骤④）。

"dump = 数据 + 自动生成的恢复脚本 + 环境描述" 是这套设计的核心洞见：拿到包的人不需要知道地址，也不需要问导出者"你当时怎么配的"。
对照我们手上的 2211 现场：9 个平铺 bin + 一个 25 MB 的 cpu-ap.elf，加载地址写死在客户 restore.cmm 里，没有恢复脚本、没有 CPU/MMU/感知描述、没有构建指纹。

调试器知道结构体类型与线程链表，脚本只写"问什么"。
我们 2210：爬
WHILE &p != &b
  &p = Var.Value(((mbinptr)&p)->bk)
  ...
ENDDO
调试器只认识"地址和字节"，脚本得自己复现 dlmalloc 的链表语义——于是有了事故 A/B。
这就是 §7 步骤⑤ 被称为"质变"的原因：把"爬链"换成"查询"，不是优化，是换了一件工具。
注意历史脉络：third_party\vendor\2100_trace32\ 里就有 oneos.t32（37 132 B）与 oneos.men（13 045 B），客户脚本里也有 TASK.CONFIG "~~~~/oneos.t32" + MENU.ReProgram "~~~~/oneos.men"。2100 那一代是有感知层的；2210/2211 这一代没有，只留下了 OS.PEF() / DIALOG.* 拼出来的手工外壳。

4.1 三条设计公理（与一条自我约束）

图 4-1 · 公理 → 直接后果
公理直接后果反例（现在就有人这么想）
A1 无头是一等公民
GUI 只是可插拔前端		 功能实现不写在按钮回调里；GUI 外壳只做"收集参数 + 显示结果" "先点 GUI 抓到问题，再考虑怎么自动化" ⇒ 自动化永远追着 GUI 跑

5四个契约

"契约"= 人和机器都遵守、且能被自动检查的约定。四个契约分别管：怎么起、真值在哪、功能长什么样、产出什么。

C1 · 配置分层：三份拼一份

图 5-1 · C1 合成规则（一列一份，纵向是"必须有的"，横向是"可换的"）
分层回答什么问题典型内容本仓库现状
base.t32这台机器上的 TRACE32 在哪、什么后端SYS=__T32_INSTALL__ · PBI=SIM · PRINTER=WINDOWSsim-minimal.t32（384 B）

分层以后，铁律 1（配置文件必须用空行分组）依然是硬约束：TRACE32 靠空行分组理解配置，拼接时不加空行会开出"不带 for ARM 的窗口"，然后 -s 脚本从不执行、进程挂到被杀。所以合成器必须在每份之间插空行，并由 lint 检查（见 §6）。

C2 · 平台数据化：platform.json → gen\*.cmm

图 5-2 · C2 的数据流（人只写左边，右边全部生成）
人写：platform.json 地址 / 结构体偏移 / 符号名 / 别名
带注释与单位，可 diff
→tools\gen_platform.py
生成：gen\memory.cmm &IRAM_BASE=0x10200000
&PSRAM_BASE=0x80000000 …
生成：gen\offsets.cmm &OFF_THREAD_STACK=…
（由 ELF/DWARF 校验，不靠人抄）
→
功能脚本：只写名字 Data.LOAD.Binary "&RAMDUMP\IRAM.bin" &IRAM_BASE
校验两遍：① 生成时用 pyelftools 读 cpu-ap.elf 的 DWARF，核对结构体偏移；② 运行时由强自检断言"walk 出的总量必须等于 arena 的 used"（现在这条已经跑通：6028 块 / Σsize 0x17CE08 vs arena used 0x17CEC0，差 184 B）。
为什么偏移必须由 ELF 校验，而不是人抄
结构体偏移是"固件一改就失效"的值，而且失效方式通常是读到错的地址而不报错。让工具从 25 MB 的 cpu-ap.elf 里读 DWARF，重新构建后 gen\offsets.cmm 自动更新——这是把"记得改"变成"不可能忘"。
为什么禁手改 gen\
生成物的头部写一行 ; AUTO-GENERATED from platform.json — DO NOT EDIT；lint 检查"若 platform.json 的 sha256 与 gen\ 头部记录不一致 ⇒ 报错"。同一条思路已经用在仓库的编码闸门上（清单来自 git ls-files，不硬编码）。

图 5-3 · C3 的接口头与它在两条通道里的位置

; @platform:  2210
; @entry:     do heap.cmm &ARENA_SYM &TAG     ; 接口（怎么被调用）

注册表 features.json 只是把同样的字段集中一份，让驱动器、GUI 生成器、等价判定、AI 都从同一处读。当前 cmm\functions.json 已经具备 name/kind/button/safe/equiv/gui/vendor/desc/body 八个字段，扩展路径明确。
#lint 规则为什么必须有怎么判
1头部字段齐全（@id/@entry/@output/@requires/@interactive）没有 @interactive 就不知道这个功能能不能进无头链解析前若干行，缺字段即失败
2platforms\*\features\*.cmm 里禁止 DIALOG.* / STOP / AREA.view铁律 2：SCREEN=OFF 下 DIALOG.* 永久挂死，无超时无报错正则命中即失败
3禁止绝对路径（[A-Za-z]:\\）公开仓库 + 换机器 ⇒ 机器路径只能进 local\正则 + 白名单（注释里的示例除外）
4每个 WHILE 必须有步数上限（&budget 或计数器）事故 A/B：客户脚本就是没有上限才静默自旋统计 WHILE 与其作用域内是否有 budget 变量
5配置文件必须空行分组（含合成后的 local\*.t32）铁律 1：违反 ⇒ 脚本从不执行、进程挂死检查空行分组与必需键
这五条 lint 规则合起来就是 tools\t32lint.py = 我们自己的 checkpatch.pl。它们几乎全部是从真实事故里长出来的——这正是"把踩过的坑变成机器可查的规则"的实例。

门禁的两条纪律
① 数据与代码分开期望值写在 tests\smoke\*.markers / tests\*.sha256 里，不写进脚本逻辑
② 自动发现，不硬编码清单清单来自 git ls-files（这就是编码闸门修掉一个真 bug 的方式：旧的检查脚本硬编码了 5 个改名前的配置文件名 ⇒ 全部静默 [SKIP]）
为什么回归绝不能依赖 AI
现有报告里已经写死这条：不把"确定性回归"和"AI 判断"揉成一层。门禁必须能用一条命令、在无人参与、无网络、无 AI 的情况下给出 PASS/FAIL。AI 站在下游读差异（L5），而不是站在回归路径里。
